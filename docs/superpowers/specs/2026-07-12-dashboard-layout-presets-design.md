# Dashboard Layout Presets Design

## Goal

Add three permanent layout controls to the 0rum dashboard so the operator can
reorganize every card in one click, while preserving manual drag-and-resize
customization as a personal layout.

## Approved interaction

- Place three compact icon buttons immediately to the left of the clock in the
  existing top bar.
- Keep the current 0rum visual language exactly: anthracite surfaces, thin
  borders, muted text, compact monospace controls, and the existing green active
  accent. No new blue surface, large badge, modal, dropdown, or separate page.
- The three controls are always available:
  1. `Une colonne`
  2. `Deux colonnes`
  3. `Mur aligné`
- A click applies the chosen preset immediately without reloading the dashboard.
- The active preset icon uses the same green active treatment as the market
  toolbar buttons.
- Each icon has a French `title`, `aria-label`, and `aria-pressed` state.
- The visible icon remains approximately 27 by 25 pixels, while CSS supplies a
  larger non-overlapping hit area where practical.

## Presets

GridStack keeps its current 12-column coordinate system. Every preset includes
every known `gs-id`, including cards that are currently hidden. Hidden market
cards stay hidden; when reopened they use the coordinates assigned by the
active layout.

### Une colonne

- Every card uses `x=0`, `w=12`.
- Cards are stacked in the existing operational order.
- Market cards keep height 8.
- Non-market cards keep their current useful height rather than being forced to
  a uniform height.
- This preset optimizes chart readability and accepts additional scrolling.

### Deux colonnes

- The four market cards form two rows of two: BTC H4 beside BTC M15/H1, then ETH
  beside PAXG. Each uses `w=6`, `h=8`.
- Remaining operational cards continue below in pairs of equal width (`w=6`).
- Paired cards share the same `y` and row height so their tops and bottoms align.
- The log remains full width because horizontal log reading is more useful than
  a narrow second column.
- This is the recommended comparison layout.

### Mur aligné

- Market cards remain in a two-by-two wall (`w=6`) so the fixed indicator rail
  and chart remain legible. They are not squeezed into three market columns.
- Compact operational cards use aligned three-column rows (`w=4`) with uniform
  heights within each row.
- Wide analytical content may span two columns; the event log remains full
  width.
- The result prioritizes density and aligned edges without making the trading
  charts unusably narrow.

The implementation plan will pin the exact `x`, `y`, `w`, and `h` values in one
data constant per preset. Layout definitions must not be scattered through DOM
handlers.

## Personal layout persistence

The dashboard stores two independent concepts:

- the last active mode: `column`, `two-column`, `aligned-wall`, or `custom`;
- one personal GridStack layout generated by manual drag or resize.

Rules:

1. Clicking a preset applies it and records that preset as active.
2. Applying a preset must not overwrite the saved personal layout, even though
   GridStack emits change events.
3. Any later manual drag or resize saves the new grid as the personal layout and
   changes the active mode to `custom`.
4. In custom mode no preset icon is shown as active; a small, subtle accent dot
   next to the icons indicates that the personal layout is saved.
5. Reload restores the last active mode. A preset is reconstructed from its
   canonical definition; custom mode loads the saved personal layout.
6. If the new personal-layout key is absent, import the current
   `orum-dash-layout-v3` value once so the operator's existing arrangement is not
   lost.
7. Malformed or incomplete stored layouts fall back to the recommended
   two-column preset without breaking dashboard rendering.
8. The existing reset control clears the personal layout and active-mode keys,
   then restores the recommended two-column preset.

## Component boundaries

### Markup

The top bar owns one small `nav` or `div` group with three semantic buttons.
Icons are inline SVG using `currentColor`; no icon package or network dependency
is added.

### Styling

New styles reuse existing CSS variables and control treatments. Focus-visible,
hover, active, and custom-saved states must remain distinguishable. At narrow
widths the controls may compress their gaps, but they must not push the clock
off screen.

### Layout controller

One JavaScript module section owns:

- immutable preset definitions;
- preset application;
- active-state rendering;
- personal-layout persistence and migration;
- suppression of GridStack change handling while a preset is being applied.

It reuses the existing GridStack instance and `grid.load(..., false)` behavior.
No dashboard API or server-side persistence is required; layouts remain local
to the browser profile.

## Failure handling

- If GridStack is unavailable, the dashboard keeps its existing stacked fallback
  and disables the layout controls rather than throwing.
- A storage write failure leaves the current visual layout usable for the
  session.
- A layout definition missing an item does not remove that DOM card.
- Programmatic preset changes are guarded so they cannot be misclassified as
  manual edits.

## Verification

- Static contract tests assert the three icon controls, accessible labels, and
  unchanged placement before the clock.
- JavaScript contract tests assert all preset IDs, storage-version keys, v3
  migration, and the programmatic-change guard.
- Browser verification checks each preset at the operator's normal desktop
  viewport, then drags/resizes one card and confirms custom restoration after a
  reload.
- Existing market-card visibility, zoom, pan, rendering, and dashboard state
  tests remain green.
- The dashboard process is restarted only after the implementation and complete
  test suite pass, using the operator's explicit restart confirmation at that
  time.

## Out of scope

- Cloud or account-level layout synchronization.
- Multiple named personal layouts.
- Mobile-specific preset variants.
- Changing card content, chart behavior, colors, typography, or the overall
  dashboard information architecture.
