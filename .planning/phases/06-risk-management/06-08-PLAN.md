<objective>
Wire `RiskGateRunner.evaluate` into `src/pipeline/runner.py` as a new step inserted between `apply_quota` (step 5) and `_persist` (step 6) — the conceptual "step 5.5" per CONTEXT D-03. Per Pitfall 4, the risk reads MUST run in their own short-lived `AsyncSessionLocal` context that closes BEFORE `_persist` opens its persistence transaction. Per the existing pattern (`src/pipeline/runner.py:94-102`), risk-rejected candidates are added to the `status_map` with status "REJECTED" so `_persist` writes them as `CandidateSignalORM(status='REJECTED')` and skips creating any `ApprovedSignalORM` for them.

This plan does NOT modify `_persist()` itself — `_persist` already reads from `status_map` and only iterates `approved_ranked` for `ApprovedSignalORM` creation; passing it the post-risk `approved_ranked` is sufficient.

**Note on ApprovedSignalORM.risk_check_passed:** CONTEXT.md describes `risk_check_passed` as flipping to False on rejection. This is a documentation artifact from an earlier design iteration. In the final design, risk-rejected candidates produce NO ApprovedSignalORM row at all — they are written as `CandidateSignalORM(status='REJECTED')` but are excluded from `approved_ranked` before `_persist` iterates it for ApprovedSignalORM creation. Therefore `risk_check_passed` is always True on any persisted ApprovedSignalORM row; it never reaches False in Phase 6. The field is reserved for Phase 7's use case (e.g., post-execution reconciliation), where "an approval was issued but execution was later blocked" may be a distinct state.

Output: One edited method (`PipelineRunner.run`) + one patched existing test + 2 integration tests in `tests/test_pipeline/test_runner_risk_step.py`.

Standard plan (not TDD) because the change is structural orchestration — write tests + code in one pass; the unit-level invariants are already locked by Plans 04–07.
